# N/A и legacy cache: совместимая политика проверки

7 ноября 2026 года. Ветка `audit/na-cache-compatibility`, база `5b34ea3`. Политика: **`transcript-validation-v3`**. Это продолжение `TRANSCRIPT_VALIDATION.md`; прежние строгие результаты сохранены.

**Итог:** обязательная прямая цитата для каждого N/A отменена. Отдельно проверяются структура результата, допустимость ответа, качество evidence, надёжность записи и готовность к публикации. На одних и тех же 65 сохранённых ответах новый кандидат даёт **55 valid, 5 warning, 5 needs_review, 0 invalid**. Публикуемыми по правилам кандидата считаются 60/65 вместо прежних 4/65. Это устранение лишней блокировки политикой, **не улучшение точности LLM и не подтверждение правильности всех 60 оценок**. В production изменения не подключены.

## 1. Что означает N/A

| `na_assessment.status` | Основание | Действие |
|---|---|---|
| `valid` | N/A разрешён, есть содержательное объяснение применимости; либо есть привязанное к данным решение человека | Прямая цитата необязательна. Сохраняется исходный N/A |
| `unsupported` | Обоснование отсутствует, состоит из общей заглушки или выражает неопределённость вместо неприменимости; также сюда относится устаревшее решение о применимости | `needs_review`, запросить обоснование/evidence |
| `invalid` | N/A запрещён критерием либо привязанное решение reviewer подтверждает, что критерий применим | Структурно запрещённый ответ — `invalid`; смысловое противоречие разрешённого ответа — `needs_review` для исправления человеком |

**Важная граница:** `valid` здесь означает, что объяснение прошло политику валидации. Содержательный текст модели сам по себе не доказывает истинность условия. Для такого ответа сохраняются `basis: documented_condition`, `independent_semantic_verification: false` и `evaluation_correctness: not_independently_verified`. Валидатор не является вторым семантическим LLM и не способен надёжно отличить всякое правдоподобное, но ложное объяснение.

Не требуется повторять ключевые слова чек-листа: русское, английское и казахское объяснение могут описывать отсутствие события иначе. Короткое «Чат оборван» не отвергается из-за произвольной длины. «Неизвестно, невозможно определить по записи» не превращается в допустимое N/A.

Если человеку известно, что N/A неверен, `reviewEvaluation(..., { applicability })` принимает отдельное решение: `source: human_review`, reviewer, applies, reason, SHA-256 транскрипта и чек-листа. При несовпадении входов решение не переиспользуется. Эти данные должен формировать доверенный review-процесс, а не модель. Новый человеческий review в этой работе не выполнялся; данный путь проверен искусственными fixtures.

Ответы не переписываются: N/A не превращается автоматически в yes/no. Вес и знаменатель вычисляются существующим scoring по исходным ответам, а спорный итог остаётся предварительным.

## 2. Четыре статуса и отдельные измерения

| Статус результата | Публикация по политике кандидата | Значение |
|---|---|---|
| `valid` | Разрешена | Автоматические проверки не нашли блокеров |
| `warning` | Разрешена с видимым предупреждением | Совместимость/контекст legacy evidence требует внимания, но ответа валидатор не меняет |
| `needs_review` | Только предварительный score | Неопределённость может затрагивать оценку или критический вердикт; требуется проверка |
| `invalid` | Итог не подтверждается | Неполный/невалидный вход, недопустимый ответ, структурная ошибка или противоречивый gross flag |

Приоритет: `invalid > needs_review > warning > valid`. Предупреждение не отменяет блокер. Для структурно невалидного результата баллы не рассчитываются. Если структура ответа корректна, но evidence требует проверки, предварительный расчёт допустим; `confirmed_total` остаётся null.

В DTO `dimensions` выделены:

- `schema_validation` — форма и обязательные поля;
- `verdict_validation` — ограничения ответа и известные противоречия;
- `evidence_validity` — ссылки, цитаты, роли и формат;
- `transcription_reliability` — обнаруженные риски записи;
- `provenance` — связь cache/probe с полным входом;
- `evaluation_correctness` — отдельно указано отсутствие независимой проверки либо противоречие reviewer;
- `publication_readiness` — общий статус и publishable.

«Автоматически прошёл валидацию» не означает «подтверждён человеком». Отсутствующая legacy-ссылка не доказывает неверный ответ, а существующая цитата не доказывает смысловую правильность вердикта.

## 3. Legacy-совместимость и сохранённые ограничения

Старые cache без версии, а также известные версии v1/v2 повторно проверяются текущими правилами в режиме legacy. Cache с версией v3 проверяется в режиме current; неизвестная версия требует review. Сторонний объект модели не должен выбирать этот режим: его назначает доверенный загрузчик.

Совместимые исключения ограничены:

1. Обоснованный N/A может иметь только `na_condition` или объяснение без цитаты — и в current, и в legacy.
2. Недостающий source anchor обычного legacy-вердикта даёт warning, а не объявляет ответ неправильным. Для нового результата этот пропуск по-прежнему требует review.
3. Клиентский повторный вопрос может быть контекстным evidence для пониженного c06 в старом результате; выдаётся warning о недостающем парном ответе оператора. Полный балл c06 по одной клиентской реплике не получает такого исключения. Правило действует только для неизменённого определения исходного критерия.
4. Старый c08=no без explicit source anchor может получить warning: отсутствие события оценивается по разговору целиком. Это осознанное исключение политики для legacy, а не доказательство отсутствия нарушения; его должен согласовать владелец безопасности/QA до интеграции.

**Не смягчались:** отсутствующий/устаревший probe, несовпадение cache input, повреждённые цитаты и индексы, положительный c08 без evidence, положительная идентификация без evidence, ложное присвоение приветствия бота оператору, неизвестная версия валидации и ошибки обязательных полей.

Предупреждение о записи блокирует затронутые критерии, если может изменить их ответ. Неиспользованный системный/ботовый фрагмент может дать warning без блокировки. Неопределённый фрагмент оператора может влиять на вывод «нарушений нет» или на отсутствие события для N/A. Уже подкреплённый положительный c08 не исчезает из-за другого, неиспользованного фрагмента.

`revalidateCachedEvaluation()` ничего не исправляет и не записывает в cache. Версия валидации отделена от версии промпта: изменение валидатора не должно само вызывать платную генерацию повторно. При смене критериев или transcript старые fingerprints не подходят.

| Метрика политики | Строгий v2 | Совместимый v3 |
|---|---:|---:|
| Допускаются к публикации | 4/65 | 60/65 = 92,31% |
| Требуют review/исправления | 61/65 | 5/65 = 7,69% |
| valid | Не разделялось | 55 |
| warning | Не разделялось | 5 |

| invalid | Не разделялось | 0 |

Повторная проверка **65 реальных файлов cache** дала те же статусы. Для 99 ответов N/A обоснование прошло политику; unsupported/invalid N/A в этом сохранённом наборе автоматически не установлены. Это не новая экспертная разметка и не измеренная 100% правильность применимости.

56 результатов перестали блокироваться. Цель не заключалась в заданном publishable rate: решения следуют явным правилам и regression tests. Исходные ответы, gold, cache, DEV и старый строгий отчёт сверены по SHA-256 до и после runner — изменений нет.

## 5. Метрики модели остались прежними

Сохранённые ответы сравнивались с теми же 19 reviewed DEV-gold диалогами:

| Показатель | Значение |
|---|---:|
| Strict accuracy | 91,45% |
| Lenient accuracy | 96,71% |
| c08 recall | 7/7, FP 0 |
| MAE score | 6,06 |

Модель заново не вызывалась. Ни 60/65 publishable, ни прохождение unit tests не подтверждают улучшение accuracy/fairness. Ранее рассчитанные downward/upward disagreement proxies — 7,69% и 2,88% на 104 сопоставимых weighted-парах — также не являются аудио-подтверждёнными False Penalty/Pass Rate. N/A mismatches учитываются отдельно.

Например, для `p1-ru-025/c02` основной gold — yes, модель — na, но na перечислен как допустимая альтернатива. Такой случай нельзя объявить неверным только из-за отличия от основного gold. В `p1-ru-029/c02` остаётся расхождение gold=na, model=no. Новая проверка совместимости сама его не исправляет.

Scoring и данные взяты из рабочей базы этой ветки, а не из меняющегося параллельно main. Производственный результат всего приложения в этой работе не тестировался.

## 6. Тесты и воспроизведение

```bash
python eval/fairness/run-compatibility.py
```

Runner запускает Python-тесты, три Node test-файла, существующие scoring self-tests, полный replay и подготовку A/B-плана. Новые зависимости не нужны. На проверенной Windows-машине использован настоящий Python 3.14.7 по полному пути, поскольку alias WindowsApps не работает.

| Проверка | Результат |
|---|---:|
| Node tests | 80/80 |
| Python unittest | 8 тестов, включая adversarial subtests; проходят |
| Adversarial guard | 18/18 |
| Прежние development fixtures | 19/19 |
| Прежние synthetic fixtures | 10/10 |
| Scoring self-tests | 7/7 |
| Команды runner | Все exit code 0 |
| Protected input SHA-256 | Не изменились |

Тесты отдельно проверяют три NA-состояния, короткие и разноязычные объяснения, unsupported-причины, конфликт с привязанным человеческим applicability review, предупреждение вместо блокировки для ограниченных legacy-случаев, отсутствие ослабления c08/идентификации, влияние uncertainty на конкретный критерий и неизвестную версию cache. Синтетическое человеческое решение в тесте не выдаётся за реальный review.

Артефакты:

- `eval/runs/transcript-compat-audit.json` — статусы всех 65 и cache, сравнение с v2, метрики;
- `eval/runs/transcript-compat-tests.json` — команды, результаты, hashes;
- `eval/runs/transcript-compat-guard.json` — исходные probe;
- `eval/runs/transcript-compat-preview.md` — таблицы критериев с NA/evidence/reason/uncertainty/status;
- `eval/runs/transcript-compat-audio-queue.json` — незаполненные человеческие аудиорешения;
- `eval/runs/transcript-compat-comparison-plan.json` — подготовленный план, не выполненный прогон.

Полный `scripts/check.sh`, браузерный сценарий и платный end-to-end inference не выполнялись. Офлайн-формат не подключён к UI.

## 7. Что осталось до интеграции

**Аудио.** Три спорных звонка не прослушаны человеком в рамках этой работы. В очереди сохранены исходные слова, timestamps и индексы; verified wording, reviewer, decision и score effect остаются null. Исходная запись не заменялась предположением.

**Контролируемый LLM-прогон.** Подготовлен manifest 19 DEV-пар: общий model/checklist/schema, отдельные хэши baseline/candidate messages и одна версия валидации для обеих сторон. Generation settings и budget cap намеренно не заданы. Для исторических ответов полная совместимость generation settings не подтверждена — нельзя без проверки назвать их контролируемой baseline-стороной. Manifest не содержит режима выполнения API.

Если обе стороны потребуют свежей генерации, это 38 первичных ответов, максимум 76 вызовов при двух попытках на сторону/диалог. Это **не разрешение на расходы и не оценка цены**. До вызовов нужны явный бюджет и заморозка одинаковых параметров. Cache генераций должен учитывать полные messages/schema/settings; validation version хранится отдельно и не должна инвалидировать генерации автоматически.

**Независимый тест.** Нового unseen human-reviewed набора нет. Все использованные здесь fixtures и DEV-gold уже относятся к разработочным данным. После заморозки промпта требуется новый RU/KZ/EN набор и оценка всех входов, а не только опубликованной подвыборки. Вместе с accuracy нужно показывать review/publishable rate, N/A mismatches и долю исключений из агрегатов.

**Решение владельца.** Передавать на code review можно новую политику, cache adapter, тесты и формат sidecar. До production требуется согласовать legacy-исключения, особенно c08=no без anchor, проверить пять review-случаев и выполнить контролируемое сравнение. Наличие warning не должно быть скрыто от пользователя.

Frontend/backend, scoring, исходный dataset и gold не менялись. Работа выполнена без платных API, commit, push, PR, merge или deploy.
