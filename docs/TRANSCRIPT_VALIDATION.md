# Transcript validation: усиление guard и кандидата evaluator

Рабочая ветка: `audit/transcript-validation`, база `fbb45c2`. Это продолжение `TRANSCRIPT_FAIRNESS.md`. Проверки выполнены локально, без платного inference, изменения production и публикации ветки.

**Результат:** устранены воспроизведённые ложные представления; кандидат больше не подтверждает результат без свежей проверки транскрипта, обязательных полей и исходных evidence. Повторно проверены все 65 сохранённых DEV-результатов и 65 соответствующих файлов cache. Эти проверки подтверждают защитные свойства кода, а не повышение LLM-accuracy.

## Что изменено

| Компонент | Изменение |
|---|---|
| `eval/transcript_guard.py` | Отрицания, неполное представление, code-switching, исключение «this is fine / a problem / Freedom Brocker», формы «Я Лера из поддержки» и «I'm Maya from support» |
| Guard provenance | Версия `transcript-guard-v2`, ID разговора, SHA-256 транскрипта, первый индекс оператора, отметка выполнения quality checks и список предупреждений |
| `eval/fairness/validation.mjs` | Проверка входа, чек-листа, ответов, metadata, summary, allowed answers, оригинальных цитат, индексов, диапазонов, ролей и provenance |
| `evaluator-candidate.mjs` | Fail-closed review, отсутствие расчёта баллов для невалидного/неполного результата, двусторонняя проверка противоречия c01 с guard, отдельный статус каждого критерия |
| Cache revalidation | Каждый переданный cache hit проходит те же проверки; другая версия/содержимое чек-листа или транскрипта запрещают подтверждение результата |
| Динамический чек-лист | Специальные правила ролей и c01 привязаны к точному определению исходного критерия; изменение определения отключает прежнее правило. Из промпта также убирается специфичное уточнение c01 |

Исходные разговоры и ответы не исправлялись. `no` не превращается в `yes`; неопределённость не превращается в N/A; веса и знаменатель не меняются. Зафиксированный c08 остаётся видимым даже при общем статусе review.

Guard распознаёт только ограниченный набор форм, а не любое допустимое имя. Code-switching при неоднозначном соответствии языку клиента вызывает review. Маскированное имя остаётся гипотезой согласуемой политики, а не новой официальной нормой.

## Повторная проверка реального DEV и cache

Проверены все восемь критериев в каждом из **65 сохранённых результатов**, включая исходные индексы, цитаты, допустимые значения и обязательные поля. Дополнительно прочитаны **65 реальных файлов `eval/cache/eval/`**, найденных по существующей формуле ключа: prompt version, модель, ID, полный transcript, criteria. Cache не переписан; новых запросов модели нет. Весь сетевой fetch внутри audit-скрипта запрещён.

| Строгая политика кандидата | Диалоги |
|---|---:|
| Проходят автоматическую структурную проверку | 4/65 |
| Требуют review | 61/65 = 93,85% |
| Нет исходного anchor хотя бы у одного вердикта | 58 |
| Evidence роли оператора не подтверждено выбранным фрагментом | 5 |
| Неподходящий `na_condition` | 1 |
| Неопределённость начала звонка | 3 |

Причины пересекаются. Это **не означает 61 неверную оценку модели**. В 58 разговорах преобладает новая, более строгая проверка: одного текста `na_condition` недостаточно, нужен ещё индекс или диапазон исходного разговора. Прежний контракт допускает такой condition-only evidence; следовательно, это разрыв между новой политикой качества и текущими данными, а не автоматически объявленная ошибка JSON-схемы.

Эту политику нельзя незаметно подключать к production: она отправляет на review почти весь сохранённый набор. Нужно согласовать достаточность evidence для N/A, добавить реальные checked ranges при генерации и измерить нагрузку на review. Автоматически дописывать диапазоны или цитаты к старым ответам нельзя.

Конкретные находки:

- `p1-ru-010`, c08: ответ `no` сопровождается evidence `na_condition`, хотя c08 не допускает N/A. Сохранённый файл cache: `eval/cache/eval/5947d4572144220ba4fa27ea48ee2067c9699d99.json`. Значение ответа не менялось, evidence требует исправления владельцем после проверки.
- `p1-ru-009`, `p1-ru-022`, `p1-kz-008`, `p1-en-010`, `p1-en-013`: c06 опирается на клиентские реплики без operator anchor в выбранном evidence. Повторный вопрос клиента может быть полезным контекстом, но для вывода об ошибке сотрудника следует указать также ответ/пропуск оператора. Сама оценка не объявлена неверной.
- `p1-ru-003:10` и `p1-en-001:9`: найдены ограничения guard на конструкциях с «из поддержки / from support». Добавлены регрессии; после исправления противоречий c01 guard с сохранённой моделью на этих случаях нет. Это доработка на DEV, не независимый тест.
- `p4-ru-002:2`, `p4-ru-005:16`, `p4-ru-004:14`: остаются в очереди аудиопроверки.

В этом replay использован прежний общий `freedom-chat@1`, поскольку именно ему соответствуют сохранённые результаты и cache. В доступной командной ветке `origin/team/v2-bright-product` уже есть speech-adapted checklist (`4438bbb`, `data/checklists/freedom-call-v1.json`). Его не копировали и не изменяли. Cache чатового чек-листа нельзя выдавать за результат нового звонкового чек-листа; текущая повторная проверка не подтверждает интеграцию этого отдельного изменения.

Полный отчёт: `eval/runs/transcript-validation-audit.json`. Старые отчёты не перезаписаны.

## Метрики: что измерено, а что нет

Исходные ответы модели не менялись. Повторное сравнение с 19 reviewed DEV-gold диалогами даёт прежние **91,45% strict**, **96,71% lenient**, **MAE 6,06**, **c08 recall 7/7**, FP 0. Сохранение семи положительных c08 также проверено отдельным тестом кандидата при отсутствии probe: флаги остаются видимыми, подтверждение итогового score блокируется.

Для разработочной диагностики дополнительно посчитано направление расхождений с основным gold-ответом:

| Показатель-прокси | Результат |
|---|---:|
| Сопоставимые weighted-пары без N/A | 104 |
| Балл модели ниже основного gold | 8/104 = 7,69% |
| Балл модели выше основного gold | 3/104 = 2,88% |
| Ниже gold с исключением `also_acceptable` | 3/104 = 2,88% |
| Выше gold с исключением `also_acceptable` | 1/104 = 0,96% |
| N/A mismatches, не входящие в этот знаменатель | 2 |

Это **downward/upward disagreement rates**, условно названные в JSON `false_penalty_proxy_pct` и `false_pass_proxy_pct`. Они не являются проверенными False Penalty Rate / False Pass Rate относительно аудио или новой экспертной разметки. В знаменатель входят сопоставимые weighted-пары; c08 измеряется отдельно. Нельзя сравнивать эти числа с иным определением знаменателя без пересчёта.

Для нового промпта нет измеренной accuracy или fairness: он не запускался. Нет новой независимой человеческой выборки. Ручная семантическая проверка всех 520 вердиктов и всех аудиозаписей не выполнена; выполнен полный структурный replay.

## Формат аналитики

Для каждого критерия кандидат теперь возвращает:

| Поле | Значение |
|---|---|
| `answer` | Исходный ответ модели без исправления |
| `score` | Детерминированные баллы; `null`, если вход не прошёл валидацию |
| `verdict` | passed / partial / failed / not_applicable / violation / no_violation / needs_review |
| `evidence` | Исходные ссылки и цитаты, без автоматической замены |
| `explanation` | Исходное объяснение |
| `transcription_warning` | Только предупреждение о неопределённости записи |
| `validation_warnings` | Отдельные ошибки schema/provenance/cache/evidence |
| `review_status` | automated_validated / awaiting_verification |

`automated_validated` означает прохождение ограниченной автоматической проверки, **не подтверждение человеком и не гарантию смысловой правильности**. При любом блокере `confirmed_total=null`, а флаг c08 не исчезает. Невалидный/неполный результат не передаётся scoring engine.

Готовый пример с таблицами для `p1-ru-002` и `p4-ru-005`: `eval/runs/transcript-validation-preview.md`. Это офлайн-экспорт для review, а не изменение интерфейса. Frontend, backend и рабочий evaluator не затронуты.

## Аудио, независимый тест и интеграция

`eval/runs/transcript-validation-audio-queue.json` содержит исходные фразы трёх звонков, индексы, исходные timestamps и endpoint аудио. Поля фактически произнесённых слов, исправленной транскрипции, reviewer, полноты начала записи и влияния на score оставлены **null**. Прослушивание не имитировалось, человеческие решения не выдумывались.

Перед интеграцией необходимо:

1. Прослушать очередь и заполнить реальные решения; отдельно отличить отсутствующее начало записи от отсутствующего действия. Сохранить исходный текст рядом с исправленной версией, не перезаписывать dataset.
2. Согласовать voice-checklist и checked-range evidence для N/A; не использовать `needs_review` как N/A и не менять знаменатель самостоятельно.
3. Включить проверку каждого cache hit в рабочем API после согласования политики. Текущий helper и replay её демонстрируют, но production его пока не вызывает. Provenance должен формировать доверенный guard, не LLM и не клиентский произвольный объект.
4. После разрешения на платные вызовы сравнить старый и новый промпты с одинаковой моделью, параметрами и чек-листом; показать отдельные показатели ошибок и покрытие review. Статистику проверенных/ожидающих публиковать вместе со средним score, чтобы исключения не завышали его скрыто.
5. Проверить замороженный кандидат на новой человеческой выборке. Сохранённый DEV и все использованные здесь fixtures уже являются разработочными данными.
6. Только после контролируемого сравнения согласовать additive API-контракт и UI. Не выдавать существующий offline sidecar за внедрённый рабочий pipeline.

Безопасный предмет code review: guard, валидатор, cache helper, fixtures, тесты и документация. Блокеры интеграции: не согласована строгая evidence-политика, 93,85% pending на старых результатах, нет аудиопроверки, новой человеческой выборки и LLM A/B-прогона. Автоматического rollback eval-v4, правок gold, коммитов, push, PR или merge в этой работе не было.
